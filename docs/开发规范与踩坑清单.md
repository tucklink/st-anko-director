## 1. 扩展是怎么被加载的（源码事实）

理解这一段，能解释绝大多数「我的扩展为什么没加载 / 加载顺序不对 / 拦截器不执行」。

### 1.1 发现与清单

1. 前端请求 `/api/extensions/discover` 拿到 `{name, type}[]`，`type` 含 `global` / `local` / `system`。
2. 对每个目录 `fetch('/scripts/extensions/<name>/manifest.json')`。
3. **拿不到或解析失败的直接丢弃**，只在这个位置留一行警告：
   `Ignoring extensions without a loadable manifest.json:`（【源码】`extensions.js:1804`）。

所以「扩展列表里根本没有我」几乎一定是 `manifest.json` 路径不对或 JSON 语法错误。

### 1.2 加载顺序：`loading_order` 有个 NaN 坑

```js
const sortManifestsByOrder = (a, b) =>
    parseInt(a.loading_order) - parseInt(b.loading_order)
    || String(a.display_name).localeCompare(String(b.display_name));
```
（【源码】`extensions.js:49`）

`parseInt(undefined)` 是 `NaN`，而 `NaN` 是 falsy —— **只要参与比较的任意一方没写 `loading_order`，
这一对的比较就整体退化成按 `display_name` 字典序**，另一方的数字顺序被无视。
文档说「不写就用 display_name 兜底」，但没说这个退化是**成对**发生的。

**结论**：要保证顺序，就别只给一个扩展写 `loading_order`。要么都写，要么接受字典序。
习惯取值参考官方扩展：`Extension-Dice` 用 `5`，`Extension-TopInfoBar` 用 `100`，骨架默认 `100`。

### 1.3 入口脚本是怎么执行的

```js
const script = document.createElement('script');
script.type = 'module';
script.src = `/scripts/extensions/${name}/${manifest.js}`;
script.async = true;
document.body.appendChild(script);
```
（【源码】`extensions.js:813-841`）

三个直接后果：

- **是原生 ESM**：可以用 `import` / `export` / 顶层 `await`；模块作用域里的变量不会污染全局。
- **是 async 的 `<script>`**：不保证和你以为的顺序同步，别依赖「另一个扩展已经加载完」。
- **相对导入基准是扩展自己的 URL**，即 `/scripts/extensions/third-party/<目录名>/`。
  这就是官方模板里 `../../../extensions.js`（→ `/scripts/extensions/extensions.js`）和
  `../../../../script.js`（→ `/script.js`）的由来。
  **用户级安装和全用户安装的 HTTP 路径相同**，所以这套相对路径在两种安装下都成立
  （服务端会把 `data/<user>/extensions/` 也挂到该 URL 下）。

配套的 CSS 是插一个 `<link id="<name>-css">`，**所以 manifest 的 `css` 路径写错只会静默不出样式**，不会阻止加载。

### 1.4 生命周期钩子（⚠️ 见 §0.0：**1.14.0 完全忽略这一节**）

```js
const url = `/scripts/extensions/${name}/${manifest.js}`;
const module = await import(url);
const hookCallResult = module[hookFunctionName]();
// Promise.race([..., delay(5000)]) → 超时只 warn
```
（【源码】`extensions.js:406-466`，**release 分支**；1.14.0 没有这段代码）

- 钩子的**键固定 7 个**：`install` `update` `delete` `clean` `enable` `disable` `activate`；
  **值**才是你自己起的导出函数名。
- 值必须是入口模块的**具名导出**（`export function onInstall()`），不是 `globalThis` 上的函数。
- 每次调用钩子都会 `import(url)` —— 模块被缓存，所以你模块里的状态在 `disable`/`enable` 之间是**保留**的。
- **5 秒超时**，超时只告警、继续执行。
- 调用时机：`activate` 在 script+style 加载完之后（`extensions.js:637`）；
  `enable`/`disable` 在**写设置之前**（`extensions.js:474/491`），且默认随后 `location.reload()`。

**⚠️ 1.14.0 上的实际行为**：`hooks` 字段被忽略 → 这些导出函数**永远不会被调用**。
所以初始化**不能**依赖 `activate`，禁用清理**不能**依赖 `onDisable`。
本插件（安科导游）的做法：
1. 初始化挂模块顶层的 `APP_READY` 监听器（它在页面已就绪时会对新监听者自动重放，所以不会错过时机）；
2. 仍然把 7 个钩子写在 `manifest.json` 里（更新的版本会调，属前向兼容），但**只当锦上添花**；
3. 「我是不是被禁用了」在**读路径**上自己判断
   （`getContext().extensionSettings.disabledExtensions.includes(扩展目录名)`，
   【源码】`extensions.js:134/428`），这样走 API 禁用（`reload:false`）时也会安静下来。

### 1.5 生成拦截器

```js
if (typeof globalThis[interceptorKey] === 'function') {
    await globalThis[interceptorKey](chat, contextSize, abort, type);
}
```
（【源码】`extensions.js:2033-2046`）

- 名字来自 `manifest.generate_interceptor`，**从 `globalThis` 取**。模块内定义的函数取不到。
- 四个参数：`(chat, contextSize, abort, type)`。
  - `chat`：即将用于构建提示词的消息数组。**它就是真实聊天记录**，改动会落到存档里；
    想临时改就 `structuredClone`。
  - `contextSize`：本次上下文的 token 数。
  - `abort(immediately)`：调用即中止生成；传 `true` 还会阻止**后续扩展**的拦截器。
  - `type`：`'normal'` / `'quiet'` / `'regenerate'` / `'swipe'` / `'impersonate'` 等。
- 按 `loading_order` 顺序串行执行，**每个都 await**，异常被 try/catch 吞掉并 `console.error`。
- **只在 `dryRun === false` 时调用**（【源码】`script.js:4562`）。

  但「只在非 dry run 时调用」**并不等于**「后台生成不会触发拦截器」。逐个 API 核对如下：

  | 调用方式 | 会触发拦截器吗 | 源码依据 |
  | --- | --- | --- |
  | 正常发送 / 重新生成 / swipe / impersonate | ✅ 会，`type` 为对应值 | `script.js:4562-4564` |
  | `generateQuietPrompt()`（自动总结、变量更新、翻译这类后台调用） | ✅ **会**，`type === 'quiet'` | `script.js:3108` 调 `Generate('quiet', generateOptions)`，**没有传 `dryRun`**，所以默认 `false` |
  | `generateRaw()` / `generateRawData()` | ❌ **不会** | `script.js:4000` 起自己组装 prompt，只发 `GENERATE_AFTER_COMBINE_PROMPTS` / `CHAT_COMPLETION_PROMPT_READY`，**完全不经过 `Generate()`** |

  **结论**：在拦截器里调 `generateQuietPrompt()` 会再次进入拦截器（可能是你自己的，也可能是别的扩展的），
  这是真实存在的自我触发/放大路径；调 `generateRaw()` 则不会。
  骨架对 `type === 'quiet'` 直接 return，就是为了切断这条路径。

  官方内置的 Vector Storage 扩展就是活证据 —— 它自己的拦截器第一件事就是跳过 quiet：
  ```js
  // public/scripts/extensions/vectors/index.js:776-779
  async function rearrangeChat(chat, _contextSize, _abort, type) {
      ...
      if (type === 'quiet') {
          return;
      }
  ```
  对照：**函数工具调用**在 `quiet` / `impersonate` / `continue` 下**不会执行**
  （【源码】`tool-calling.js:694-697`）。两者行为不一致，不要互相类推。

### 1.6 i18n 的加载时机

```js
// activateExtensions 里，先 locale，再 script + style
const promise = addExtensionLocale(name, manifest).finally(() =>
    Promise.all([addExtensionScript(name, manifest), addExtensionStyle(name, manifest)]));
```
（【源码】`extensions.js:631-633`）

`addExtensionLocale` 只取 `manifest.i18n[当前语言]` 一个文件，`fetch` 后 `addLocaleData(locale, data)`。
`addLocaleData` 里有两道闸（【源码】`i18n.js:22-39`）：

1. `localeData` 尚未加载 → 打印 `Localization data not loaded yet` 并**直接放弃**；
2. 传入 locale ≠ 当前 locale → 静默忽略；
3. 键已存在 → **不允许覆盖**。

### 1.7 常用事件的实参（逐行核对 `release` 分支 `script.js` 得到）

【文档】特意警告过「事件实参不统一」，所以这里逐个钉死。做消息/提示词处理的扩展最需要这张表：

| 事件 | 实参 | 源码位置 |
| --- | --- | --- |
| `MESSAGE_RECEIVED` | `(messageId: number, type: string)` | `script.js:3799`（流式收尾）、`6691/6716/6738/6781`（非流式）、`7705`、`9916` |
| `CHARACTER_MESSAGE_RENDERED` | 同上，紧随 `MESSAGE_RECEIVED` 之后 | 同上各行的下一行 |
| `MESSAGE_SENT` | `(insertAt: number)` 消息下标 | `script.js:5910/5917` |
| `USER_MESSAGE_RENDERED` | 同上 | `script.js:5912/5919` |
| `MESSAGE_EDITED` | `(this_edit_mes_id: number)` | `script.js:8405` |
| `MESSAGE_SWIPED` | `(mesId: number)` | `script.js:10315` |
| `MESSAGE_DELETED` | `(chat.length: number)` —— **是长度，不是被删的 id** | `script.js:1615/1703` |
| `CHAT_CHANGED` | `(getCurrentChatId())` | `script.js:1727`、`group-chats.js:322` |
| `GENERATION_STARTED` | `(type, options, dryRun: boolean)`，`options` 含 `automatic_trigger`、`quiet_prompt`、`force_chid` 等 | `script.js:4299` |
| `GENERATION_ENDED` | `(chat.length: number)` | `script.js:3536` |
| `GENERATION_AFTER_COMMANDS` | `(type, options, dryRun)`，`options` 同 `GENERATION_STARTED`。⚠️ **触发时用户消息还没进 `chat`** —— 见 §1.7.1 | `script.js:3935`（1.14.0） |
| `IMPERSONATE_READY` | `(text: string)` | `script.js:3802` |
| `TOOL_CALLS_PERFORMED` / `TOOL_CALLS_RENDERED` | `(invocations: ToolInvocation[])` | `tool-calling.js` |
| `EXTENSIONS_FIRST_LOAD` | 无参，**且在 manifest 被发现之前**触发 | `extensions.js:1798` |
| `EXTENSION_SETTINGS_LOADED` | 安装响应对象（含 `display_name`、`folderName`） | `extensions.js:1771` |

三条必须记住的细节：

- **`MESSAGE_RECEIVED` 不是「生成成功」信号**：流式输出报错时它照样会发
  （`type` 为 `swipe` / `impersonate` / `continue` 时除外，`script.js:3826-3830`）。
- **`impersonate` 不发 `MESSAGE_RECEIVED`**，改发 `IMPERSONATE_READY`（`script.js:3798-3803`）。
  只监听 `MESSAGE_RECEIVED` 的扩展会漏掉「替身发言」。
- 用 `event_types.X` 常量监听，**别手写字符串**：源码里有几处命名不一致（`CHAT_CHANGED` 的值是
  `'chat_id_changed'`、`CHAT_LOADED` 是 `'chatLoaded'`、`CHARACTER_DELETED` 是 `'characterDeleted'`、
  `GENERATION_AFTER_COMMANDS` 的值就是大写原名）。

### ⚠️ 1.7.1 `Generate()` 内部的真实顺序（改消息/提示词的扩展必读）

**`GENERATION_AFTER_COMMANDS` 触发时，用户消息还不在 `chat` 里。** 逐行核对 1.14.0：

| 行号 | 发生什么 |
| --- | --- |
| `script.js:3913` | `emit(GENERATION_STARTED, type, options, dryRun)` |
| `script.js:3925` | `processCommands($('#send_textarea').val())` —— **斜杠命令在这里执行**，所以命令不会变成聊天消息；返回 true 就直接 `return`，**后面的事件全都不发** |
| **`script.js:3935`** | **`await emit(GENERATION_AFTER_COMMANDS, type, options, dryRun)`** |
| **`script.js:4066`** | **`await sendMessageAsUser(textareaText, messageBias)` ← 用户消息在这里才 `chat.push`** |
| `script.js:4110` 起 | 组装提示词（`let coreChat = chat.filter(...)`） |

`sendMessageAsUser` 里的顺序是：`chat.push(message)` → `emit(MESSAGE_SENT, chat_id)` → `addOneMessage` → `saveChatConditional()`。

**结论（这是踩了坑才定下来的）**：

- 「把用户消息换成别的东西再让模型看到」**必须挂 `MESSAGE_SENT`**，不能挂 `GENERATION_AFTER_COMMANDS` ——
  后者触发时最后一条还是**角色的上一句回复**，「最后一条是用户消息」这个前提根本不成立。
- `MESSAGE_SENT` 还自带三道**免费**的过滤（`script.js:4060` 那段守卫）：
  `quiet` / `dryRun` / `automatic_trigger` 都不加用户消息；滑动、重新生成、续写同样不加
  —— 所以这个事件只在「真的往 chat 里加了一条用户消息」时才发，不用自己判 `type`/`dryRun`。
- 它在提示词组装**之前**发，而且 `emit` 会 `await` 监听器 —— 返回 Promise 就能挡住流程，等处理完再组装提示词。
- 用 `insertAt` 定位那条消息，**不要用 `chat.length - 1`**：插入式发送的消息不一定在末尾。

## 4. 初始化时序怎么选

| 入口 | 什么时候用 | 关键约束 |
| --- | --- | --- |
| 模块顶层（`index.js` 直接跑） | 同步、必须尽早就位的注册：拦截器、斜杠命令、宏 | 此时 DOM 可能还没就绪，别碰 ST 的 UI |
| `activate` 钩子 | 官方说法：需要在「阻塞加载层还在的时候」完成的**同步**初始化 | 5 秒超时；在 script+style 加载完之后调用 |
| `APP_INITIALIZED` 事件 | 需要改 ST 的 UI，但希望「所有扩展和 UI 元素都已就位」时 | 加载层还在，会阻塞酒馆就绪 |
| `APP_READY` 事件 | **异步**初始化：拉数据、渲染自己的面板、注册依赖 DOM 的东西 | 处理器会被 await，别在里面长阻塞 |

骨架的选择：拦截器 + 斜杠命令放模块顶层，其余全放 `APP_READY`。
因为 `APP_READY` 对「事后才挂上的监听者」会自动重放，所以无论扩展是在酒馆就绪前还是就绪后加载，
这条路径都成立 —— **不需要自己写 setTimeout 轮询或时序判断**。

> 【文档】的原话提醒：`APP_READY` 的处理器会被 await，所以官方建议「用定时器或类似机制推迟处理」。
> 骨架里就是 `setTimeout(() => void init(), 0)`。

## 6. 处理消息与提示词：五条路怎么选

| 手段 | 生效时机 | 适合做什么 | 代价 / 风险 |
| --- | --- | --- | --- |
| 正则扩展（ST 自带 Regex） | 渲染前 / 发送前 | 纯粹的文本替换、格式清洗 | 逻辑表达能力弱，无状态 |
| `setExtensionPrompt(key, value, pos, depth, scan, role)` | 构建提示词时 | **注入指令、状态栏、变量** | 写入后一直生效，**关闭时必须显式清空**；`key` 要唯一 |
| `generate_interceptor` | 生成请求发出前 | 按 `type` / `contextSize` 做条件注入、按需改消息数组、必要时中止生成 | 必须挂 `globalThis`；改 `chat` 会落到存档（官方为这类副作用打过两次补丁：PR [#3489](https://github.com/SillyTavern/SillyTavern/pull/3489)、[#3763](https://github.com/SillyTavern/SillyTavern/pull/3763)）；`generateQuietPrompt()` **会**再触发拦截器（`type === 'quiet'`，要自己排除）；抛异常会中止本次生成并弹用户可见报错 |
| 监听 `MESSAGE_RECEIVED` 等事件 | 消息写入 `chat` 后 | 解析模型输出、更新状态、写 `chatMetadata` | **每条消息都跑**，重活会卡 UI；此时消息还没渲染 |
| `messageFormatter.addHook()` | 渲染管线 | 富文本标注（ruby、tooltip）、高亮 | 官方文档标为 **staging 特性**；我们抓取的 `release` 分支里代码和 `getContext().messageFormatter` 都已存在，但**你装的发行版是否可用要实测**。钩子必须**同步**返回字符串，且每条消息都会跑一次 |

两个最常见的设计错误：

1. **在拦截器里做 `generateQuietPrompt()` 之类的后台生成** —— `generateQuietPrompt()` 不以 dry run 运行，
   所以它会**再次触发拦截器**（依据见 §1.5 的表）。骨架的做法是 `type === 'quiet'` 直接返回，另加一个重入标志。
2. **用 `setExtensionPrompt` 注入后忘了清空** —— 用户把开关关掉，注入内容还在每次请求里。
   骨架在「关闭」和 `onDisable` 两处都调了 `setExtensionPrompt(KEY, '', ...)`。

## 7. 踩坑清单

### 7.0 「只有思考、没有正文」怎么处理（**本节修正过一次，见文末"读取记录"**）

**现象**：走自定义来源（OpenAI 兼容端点）时，返回 `{content:"", reasoning:"…"}`。
插件（走 `generateRaw` 兜底）随后收到酒馆抛的 `No message generated`。

#### 复核后的正确结论（逐行核对过源码）

1. **酒馆不认为这是"错误"** —— 主聊天路径照常落库一条「正文为空 + 思考块有内容」的消息：
   - 非流式：`script.js:5093-5095` 分别抽正文与思考 → `5140` `saveReply({…, reasoning, …})` → `6284-6289` `extra['reasoning'] = reasoning; chat[…]['mes'] = getMessage;`（**空正文照样入库**）
   - 流式：`script.js:3347/3356` `chat[messageId]['mes'] = processedText;` → `reasoningHandler.process(...)`
   - **专门为这种楼层保留消息**（不删空楼的条件里明确排除了"有思考"的情况）：
     `script.js:5025` 与 `5152`：`… && ['', '...'].includes(lastMessage?.mes) && !lastMessage?.extra?.reasoning …`
   - UI 也是并列的两块：`index.html:7089-7108`（`<details class="mes_reasoning_details">` 与 `<div class="mes_text">` 并列），
     `style.css:1222` 还专门给"空正文 + 有思考"的楼层留了边距 —— **官方预期这种楼层存在**。
2. **`No message generated` 只有一处**：`script.js:3754-3755`，**在 `generateRaw` 内部**（该函数全程不看 reasoning）。
   → 所以**"退回 `generateRaw`"救不了这一轮**（同一响应照样抛）✗
3. **"只有思考算不算有效"这件事，酒馆明确留给调用方判断**：
   程序化调用拿到的是两个字段 —— `custom-request.js:472-478`
   `reasoning: extractReasoningFromData(json, { …, ignoreShowThoughts: true })`。
4. **思考的抽取与正文是两条链，互不兜底**：
   正文 `script.js:5858`（`??` 链里没有 reasoning；注意 `""` 不会触发 `??` 兜底）；
   思考 `reasoning.js:132-136`（CUSTOM 分支：`message.reasoning_content ?? message.reasoning ?? ''`）。
5. **CUSTOM 来源在酒馆面板上"没有能减少思考的开关"**：
   - `#openai_reasoning_effort` 只对 `OPENAI_REASONING_EFFORT_MODELS`（`constants.js:456-473`）里的模型才发，
     `google/gemini-3.7-flash` **不在其中**（`chat-completions.js:2005-2007`）✗
   - `#openai_show_thoughts` → `include_reasoning` **在 CUSTOM 分支根本不转发**
     （`chat-completions.js:1863-1879` 只做 `mergeObjectWithYaml(bodyParams, request.body.custom_include_body)`）
   - `reasoning_effort_types` 只有 `{auto, low, medium, high, min, max}`（`openai.js:233-240`），**没有"关闭"**；
     唯一能算到 `thinkingBudget = 0` 的是 **Google 那条服务端路径**（`prompt-converters.js:1076-1083`，`min`）
     —— 对 CUSTOM 来源不适用 ✗
   → **CUSTOM 来源唯一能改请求体的入口是 `custom_include_body`（酒馆面板上的自定义请求体）** ✓

#### 所以插件该怎么做（结论也变了）

- **不要把 `reasoning` 拼进正文当兜底** ✓（与酒馆的数据/UI 契约冲突：`index.html:7089-7108`、`script.js:6284-6285`；
  而且思考常是自我规划文本，比如实测拿到的 `I'm focusing on mapping out…` ✗ 不是可交付正文）。
- **正文空 = 这一轮没有产出**，但**不要用"再退回一次"来掩盖它** ✗ ——
  退回 `generateRaw` 只会抛出一个**掩盖真因的第二错误** ✗。应该**把第一因（含 reasoning 摘录）直接报出来** ✓。
- **诊断必须带 reasoning 摘录**（这是唯一能让人判断"端点不给正文"还是"被截断"的信息）✓ ——
  测试连接那条分支已经这么做 ✓，导演循环那两处**还没有** ✗ → 待改。
- **给用户的两条实际出路**（都不是插件能替的）：
  1. **换一个不发思考的模型**（最干净）；
  2. 在酒馆面板的 **`custom_include_body`** 里给这个端点加它自己的减思考参数。

#### 已查到的具体参数（两个来源，**有一个冲突，已标明**）

**来源 A：Google 官方 — `https://ai.google.dev/gemini-api/docs/openai`（最权威）**

Google 自己的映射表（原文照抄）：

| `reasoning_effort`（OpenAI 侧） | `thinking_level`（Gemini 3 Flash） | `thinking_budget`（2.5） |
| --- | --- | --- |
| `minimal` | `minimal` | 1,024 |
| `low` | `low` | 1,024 |
| `medium` | `medium` | 8,192 |
| `high` | `high` | 24,576 |

原文还有一句决定性的：

> "अगर आपको सोचने की सुविधा बंद करनी है, तो 2.5 मॉडल के लिए `reasoning_effort` को `"none"` पर सेट करें.
> **Gemini 2.5 Pro या 3 मॉडल के लिए, रीज़निंग की सुविधा बंद नहीं की जा सकती.**"
> （要关掉思考，2.5 模型设 `reasoning_effort: "none"`；**Gemini 2.5 Pro 或 Gemini 3 模型无法关闭思考**）

→ ① **`reasoning_effort` 是 Google 官方 OpenAI 兼容层认的字段名** ✓
→ ② **Gemini 3 关不掉思考**（厂商明文）✓ —— 只能降低
→ ③ 不指定时用**模型默认档**（Gemini 3 Flash 默认偏高）→ 这正是"思考吃满、正文为空"的来路 ✓

**来源 B：LiteLLM — `https://docs.litellm.ai/docs/providers/gemini`**

⚠️ **与来源 A 冲突的一点**：LiteLLM 说 "**3.7 and 3.8 Flash reject `minimal`**, so they get `low`"，
而 Google 的表里 **Gemini 3 Flash 的 `minimal` → `minimal`** ✗。
**两个来源打架 → 不许当结论**：实操按"**先试 `minimal`，端点报错再改 `low`**"，
两条路的结论都是"把思考压到最低档" ✓。

LiteLLM 还提到一条**未在 Google 文档中核对**的：Gemini 3 建议**不要设 `temperature`**
（原文 "Setting `temperature < 1.0` can cause: Infinite loops / Degraded reasoning performance"）
—— 标为**单来源**，实操上"留空"没有副作用，值得照做，但不当定论。

**边界（必须写清）**：以上两条都是"Google 官方 OpenAI 兼容层 / LiteLLM"的行为 ✓；
**用户那个端点是第三方实现，它认不认、转发不转发这个字段，从任何文档都看不出来，只能实测** ✓。
但字段名有厂商背书 ✓ → "先试 `reasoning_effort`"是**有依据的第一枪**，不是碰运气 ✓。

**更稳的做法（如果额度/模型可选）**：直接**换一个不是 Gemini 3 的模型**（或非思考模型）——
因为 Gemini 3 **关不掉**思考 ✓，`minimal`/`low` 只是降低 ✓，"确定能出正文"只有换模型能保证 ✓。

#### 读取记录（这一节我读错过一次，留档）

第一版规范我据 `script.js:5858` 一个函数就下了结论「酒馆从不把思考当正文 / 只有思考就是失败」✗。
实际那是**文本补全**那条路的通用抽取 ✗；**Chat Completion 的响应处理在 `openai.js` + `reasoning.js`** ✓，
而主聊天路径**不报错、还会专门保留空正文楼层** ✓。**教训：结论要落在"处理这条路径的那个文件"上，
不能拿一个同名相似的函数顶替** ✓（这条本身也是规范）。

**酒馆自己的口径（照抄，别自己发明）**：

- 正文抽取**只认这些字段，整条链里没有 reasoning**：
  `script.js:5857-5858`
  ```js
  case 'openai':
      return data?.content?.find(p => p.type === 'text')?.text
          ?? data?.choices?.[0]?.message?.content
          ?? data?.choices?.[0]?.text
          ?? data?.text
          ?? data?.message?.content?.[0]?.text
          ?? data?.message?.tool_plan ?? '';
  ```
- 思考是**另一个字段**单独抽的：`reasoning.js:112` → `data?.choices?.[0]?.message?.reasoning_content ?? ''`
- 正文清理后为空 → **酒馆直接抛错**：`script.js:3754-3756`
  ```js
  if (!message) { throw new Error('No message generated'); }
  ```

**所以插件该怎么做**：正文空 = 这一轮**失败**，退回或报错；
**不许**把 `reasoning` 当正文用 —— 那会把"端点的毛病"伪装成"用户的大纲质量问题" ✗，
而且与酒馆口径不一致（别的扩展/酒馆自身都认为这轮没产出）。

**遇到时的处置（两条都是酒馆原生杠杆，插件替不了）**：

1. **换一个不发思考的模型**（最常见、最干净）。
2. 酒馆预设里的 **`reasoning_effort`** 会随请求发出去（`openai.js:348` 定义、`452` 默认 `auto`、
   `4191` 组装进请求）—— 调低它**可能**让思考变短；
   ⚠️ **但"你的端点认不认这个字段"从酒馆源码里看不出来，必须实测**，不许当结论写。

**插件侧只做诊断，不做兜底**：正文取不到时，报错必须带上
`content 长度 / reasoning 长度 / finish_reason / 顶层键`（见 `index.js` 的 `describeShape`）——
**目的是让下一次能分清「端点压根不给正文」和「正文被截断」**（后者只是**待验证的怀疑**，见下）。

⚠️ **"额度（`max_tokens`）不够导致正文为空"这条因果，在本机源码里查不到依据** ——
ST 里**没有**任何把"思考吃光额度"与"空正文"联系起来的判定或处理代码
（`generateRaw` 只看 `extractMessageFromData`；`openai.js` 也不拿 `finish_reason` 与空正文做关联）✗。
**所以它只能算经验性怀疑，不许写成结论** ✗ —— 我自己就犯过这个错：
写死 `2048` 并声称"服务商默认不够用"，**随后被实测推翻**（传 2048 时正文照样空；
真因是 Gemini 3 默认 high 思考 ✓，见上文）。

能写成结论的只有这三条（都有出处）：

| 结论 | 出处 |
| --- | --- |
| 传值会**覆盖**预设里的 `max_tokens` | `shared.js:412` + `custom-request.js:220`（custom 在后） |
| 不传 → 该键被丢掉、服务端**原样透传** | `chat-completions.js:630/705/803/…` |
| 预设默认值是 **300** | `openai.js:373` |

⚠️ **重要更正（2026-10 补）**：上面"这条因果在本机源码里查不到依据"只对**酒馆的代码**成立 ✓ ——
**在服务商（Gemini）层面，这条因果已被多个独立来源证实** ✓✓：

- 「Gemini 2.5/3 Flash **thinking tokens consume maxOutputTokens, causing empty responses**」
  https://github.com/valentinfrlch/ha-llmvision/issues/609
- 「Gemini 3 Pro Preview returns **0 text parts - only thinking tokens generated, no actual output**」
  （**Google 官方论坛**）https://discuss.google.dev/t/gemini-3-pro-preview-returns-0-text-parts-only-thinking-tokens-generated-no-actual-output/325509/3
- 「GeminiLLM has no reasoning headroom: **thinking tokens consume max_output_tokens**」
  https://github.com/vectorize-io/hindsight/issues/3365
- 两条修法 PR：「**raise maxOutputTokens** when thinking is enabled」、
  「send thinkingLevel for 3.8 Flash **so thoughts stop eating**…」

**所以正确的因果链是**：Gemini 3 思考默认档偏高（Google 文档）→ 思考 token **计入输出上限** →
额度被吃光 → 正文分到 0 → `content: ""` → ST 只认 `content`（`script.js:5858`）→ 空正文 ✓

**结论修正为**：**降思考 + 给足额度，两条都要** ✓（不是"额度无关" ✗）——
这也解释了为什么传 2048 仍然空：**思考本身就不止 2048** ✓。
插件侧的自纠已经两类都做了：重试时同时**降思考**（`custom_include_body.reasoning_effort`）
并**放宽 `max_tokens`**（见 `index.js` 的重试分支）。

### 7.0.1 为什么"酒馆正文不空、只有插件的导演会空"（**这条才是关键差异**）

**代码事实**：酒馆**只在自己原生的 Gemini 路上**替模型限思考预算，**在 custom 路上什么都不做**。

```js
// src/prompt-converters.js:1075-1101 —— 思考预算按输出额度的比例算
case REASONING_EFFORT.auto:   return -1;                       // 交给模型
case REASONING_EFFORT.min:    return 0;                        // 完全不思考
case REASONING_EFFORT.low:    budgetTokens = maxTokens * 0.1;
case REASONING_EFFORT.medium: budgetTokens = maxTokens * 0.25;
case REASONING_EFFORT.high:   budgetTokens = maxTokens * 0.5;  // ← 上限也只有一半
budgetTokens = Math.min(budgetTokens, 24576);

// src/endpoints/backends/chat-completions.js:436-449 —— 真写进请求
const thinkingConfig = { includeThoughts: includeReasoning };
const thinkingBudget = calculateGoogleBudgetTokens(generationConfig.maxOutputTokens, reasoningEffort, model);
if (Number.isInteger(thinkingBudget)) { thinkingConfig.thinkingBudget = thinkingBudget; }
generationConfig.thinkingConfig = thinkingConfig;
```

→ 走**原生 Gemini 来源**时，**思考永远吃不光额度** ✓ → 正文不会因思考而空 ✓
→ 走 **CUSTOM 来源**时，custom 分支**只 merge `custom_include_body`**
（`chat-completions.js:1863-1879`，读者逐行核实 ✓），**没有 thinkingConfig、没有预算计算** ✗
→ 思考完全由端点决定 → Gemini 3 默认偏高 → 吃光 → 正文空 ✓

| 走哪条路 | 谁管思考预算 | 正文会空吗 |
| --- | --- | --- |
| ST 原生 Gemini 来源（makersuite / vertex） | **ST 服务端**（比例限额） | 不会 ✓ |
| **CUSTOM 来源**（本插件的导演走这条） | **没人管** | **会** ✓ |
| 非思考模型 | — | 不会 ✓ |

**所以插件的正确做法是"补上 ST 在 custom 路上不做的那件事"** ✓：
重试时塞 `custom_include_body: { reasoning_effort: 'minimal' }`（等价于给这条路补一个思考预算）
并放宽 `max_tokens` ✓ —— 见 `index.js` 的重试分支 ✓


**不是**替用户挑一个数字 ✗ —— `directorApiMaxTokens` 默认 `0` 就是这个意思 ✓。

#### B. 上游这一侧（Google / OpenRouter 官方）

| 事实 | 来源 |
| --- | --- |
| **`MALFORMED_FUNCTION_CALL` = 模型生成的调用无法解析**（Generation error code），**不是**声明不合规 | `ai.google.dev/gemini-api/docs/api-errors`："The model produced a function call that could not be parsed." |
| 声明不合规走**另一条路**：HTTP 400 `Invalid JSON payload received. Unknown name "…"`，**整请求失败** | LangChain.Utils.GoogleSchema 文档 + 论坛实例 |
| **最常触发 malformed 的形状：数组参数 / 长字符串参数** | `discuss.ai.google.dev` 帖 #93630 原文："most common when tool inputs are **arrays of objects or long strings**" |

| `$schema` 不是 Google `Schema` 的字段；OpenRouter 按 **Draft 7** 校验 tools 的 schema | Google `@unsupported_keywords`；OpenRouter `new Validator(parameters, '7')` |
| **中文 / 非 ASCII 不是问题**（未找到任何官方禁止） | 读者结论（明确标注"未找到"） |

#### C. 由此定下的三条规矩

1. **工具参数里不许有数组、不许要长字符串** ✓
   （原来的 `options: string[]`「十项长中文表」**已删** —— 它正踩在 malformed 最高发的形状上 ✗；
   十项表回到**文本协议**那条路渲染 ♛ ✓）
2. **不许写 `$schema`** ✓（Google 不认 ✓、OpenRouter 按 Draft 7 校验 ✓；
   虽然酒馆对 Gemini 会自己删掉 ✓，但别的来源会原样发出去 ✗）
3. **工具模式的 system prompt 里必须带 JSON 转义要求** ✓（有实测数据支撑 ✓）

**并且：新机制不许默认打开** ✓ ——
`useDiceTool` 默认 `false` + `DICE_TOOL_ENABLED` 硬钉 `false` 的原因，见 §7.0.2 ✓。

## 8. i18n 实操细节

1. **键 = 英文原文**，元素内容也写同样的英文，两边一致最省事：

   ```html
   <span data-i18n="Enable extension">Enable extension</span>
   <textarea data-i18n="[placeholder]Text injected before generation"
             placeholder="Text injected before generation"></textarea>
   ```

2. **语言文件的键不要带 `[placeholder]` 前缀**：【源码】`i18n.js:156` 用正则把
   `[属性名]` 剥掉后才查表，所以 JSON 里写 `"Text injected before generation": "…"`。

3. **只挂非英文语言**，键用 `lang.json` 里的 `lang` 值（`zh-cn`、`zh-tw`、`ja-jp`…）。

4. **模板渲染出来的 HTML 会自动本地化**（`renderExtensionTemplateAsync` 内部强制 localize），
   而且 `i18n.js` 还挂了 MutationObserver，**后插入的 `[data-i18n]` 节点也会被翻译** ——
   所以动态生成的界面同样能吃翻译。

5. 代码里的文案：`const { t, translate } = getContext();` → `` t`Hello ${name}` ``；
   插值占位符在语言文件里写作 `${0}`、`${1}`，**键和译文都要保留占位符**。

### 7.2 连接配置下拉"只同步一次"→ 用户选不到配置（真缺陷，2026-10-24）

**症状**：面板里「导演走哪个预设」只有「跟随当前设置」✗，用户以为预设没用 ✗。

**原因**：`syncProfileOptions()` 只在面板挂载时调一次 ✓，而 `connection-manager` 可能比插件
**晚就绪** ✗ → 那一刻列表是空的 ✓ → 之后再也不刷新 ✗。

**修法**（三重保险 + 一条兜底）：
1. 挂载后 2 秒再同步一次 ✓
2. 监听酒馆的四个事件 ✓：`connection_profile_loaded` / `_created` / `_updated` / `_deleted`
   （`events.js:77-80` 有定义 ✓，`connection-manager/index.js` 里确实会 emit ✓）。
   ⚠️ 取不到 `eventTypes` 枚举时**退回事件字符串** ✓ —— 否则 `listen(undefined, …)` 会静默注册到
   `undefined` 上 ✗（这个坑 `listen()` 已有防呆 ✓，但取不到枚举时我原来直接跳过 ✗）。
3. 用户**聚焦下拉**时再刷一次 ✓（几乎零成本 ✓）

**教训**：凡是"启动时拉一次外部列表"的地方，都要假设**对方可能更晚就绪** ✓ ——
面板类同步必须有"事件/聚焦/重试"至少一种兜底 ✗。

### 7.3 ⚠️ 改"空值的含义"= 会打断用户已有配置（2026-10-24 回归）

**症状**：用户升级后说"以前可以，现在不行" ✗ —— 而且面板上看不出任何变化 ✗。

**原因**：我把来源下拉的**空值语义**改了 ✗：
- 旧：来源留空 + 填了模型 → **同源换模型**（走服务端代理）✓ —— 用户一直在用 ✓
- 新：来源留空 = 跟随当前设置（`generateRaw`）✗，面板里填的模型被忽略 ✗

用户设置里存的是 `directorApiSource: ''` + 有模型 ✓ → 升级后**同一条设置，行为变了** ✗。

**修法**：加**设置版本迁移**（`SETTINGS_VERSION` 2 → 3）✓ ——
`source` 为空且 `directorApiModel` 有值 → 自动写成 `__same__` ✓ 并记一条日志 ✓。

**教训**：
> **凡是改变"用户已存值的含义"，必须同时写迁移** ✓ ——
> 否则等于**偷偷替换用户的选择** ✗。`SETTINGS_VERSION` 这套机制就是干这个的 ✓，
> 改语义时不用它就是漏 ✗。

### 7.4 "同源换模型"这条路**从来没应用预设**（2026-10-24 用户发现）

**症状**：用户选「同源换模型」（正文来源 + 自己填的模型），发现**预设完全没生效** ✗。

**原因**（读源码得出 ✓）：`ChatCompletionService.processRequest` **只有传了 `presetName` 才应用预设**
（`custom-request.js:540`）✓；而代理分支不传 ✗ → 在 1.14.0 里等于**一个采样参数都不带** ✗。
（1.14.0 就算传了也只取 temperature ✗ —— 见 §7.0 那条。）

**修法**：代理分支里**自己取一遍正文当前预设** ✓
`getPresetManager('openai').getSelectedPresetName()` → `getCompletionPresetByName()` →
`presetToPayload(preset, { source })` ✓，然后：
- 预设**铺底** ✓ → `...presetFields`
- **面板填了才覆盖** ✓（没填时**不要出现那个键** ✗ —— `custom-request.js:220` 是 custom 在后，
  传 `undefined` 会把预设值顶掉 ✗）
- `max_tokens` 优先级：面板 ✓ → 预设 ✓ → `directorMaxTokens()` 兜底 ✓
- **降思考重试那次也要带** ✓，否则重试等于丢预设 ✗

**教训**：
> 凡是"只有传了 X 才生效"的第三方 API，**不传就是静默不用** ✗ —— 功能测试全绿也发现不了 ✗。

### 7.5 抄预设的"请求体改写字段" → 上下文被静默删掉（2026-10-24 用户报"原文上下文直接没了"）

**症状**：导演忽然看不到之前的正文，输出像"失忆" ✗。

**原因**：`presetToPayload` 原来会把预设里的
`custom_include_body` / `custom_exclude_body` / `custom_include_headers` 一并搬进请求 ✗，
而酒馆服务端会**真的执行它们**：
- `chat-completions.js:1878` `mergeObjectWithYaml(bodyParams, custom_include_body)` —— **覆盖请求体字段**
- `chat-completions.js:2068` `excludeKeysByYaml(requestBody, custom_exclude_body)` —— **删掉请求体里的键**

预设里只要配了 `messages`（把提示词整段替换/删除是这类 hack 的常见用法 ✗），

**修法**：`presetToPayload` **只抄采样参数** ✓，这几个请求体改写字段**一律不抄** ✗。

 那是**我们自己要发的**，不是从预设搬的 ✓，两者别混 ✗。）

**教训**：
> "从别人的配置里抄字段"时，必须逐个确认**这个字段在接收端会产生什么副作用** ✓。
> 名字看起来像"预设的一部分"✗，不代表它只影响采样 ✓ —— 有的字段会**改整段请求** ✗。

### 7.8 "这压根不是我的预设"：必须显示**每个值从哪来**

### 7.9 ✅ 正确抄法：读 `chatCompletionSettings`（酒馆的实时设置），不是解析预设 JSON

**用户质问**："酒馆到底是怎么做到的，抄也不会" ✗ —— 他说得对 ✓。

**酒馆的真实做法**：
1. 你选中预设时，酒馆把预设字段**写进 `oai_settings`** ✓（`openai.js` 的 `settingsToUpdate`）
2. 之后每次请求都从这份**实时设置**取参数 ✓
3. 而 `getContext()` **把它暴露出来了** ✓：`chatCompletionSettings: oai_settings`（`st-context.js:206` ✓）

**所以正确做法**（已实现 ✓）：`settingsToPayload(ctx().chatCompletionSettings, { source })` ✓
- 字段名照 `openai.js` 的 `default_settings`：`temp_openai` / `top_p_openai` /
  `freq_pen_openai` / `pres_pen_openai` / `openai_max_tokens` / `top_k_openai` / `min_p_openai` /
  `top_a_openai` / `repetition_penalty_openai` / `seed` / `n` ✓
- `openai_max_tokens` → payload 的 `max_tokens` ✓
- **`reasoning_effort` 是字符串枚举** ✗（`low/medium/high/minimal`），按数字过滤会整个丢掉 ✗；
  `auto` = 不发送 ✓（与酒馆一致 ✓）
- `repetition_penalty === 1` 视为"不惩罚"→ 不发 ✓

**我错在哪**：一直去"解析预设对象"✗ —— 那条路要赌"预设名对得上""字段名一致"✗，
每多一个假设就多一个失败点 ✗。**读实时设置等于零假设** ✓。

**教训**：
> 抄第三方功能时，先找**它自己用的那份运行时数据** ✓（这里就是 `oai_settings`），
> 而不是去解析它的**输入文件** ✗。前者零假设，后者到处是假设 ✗。

### 7.10 ✅ 最终结论：用 `generateQuietPrompt`，不要自己拼提示词（"完全按酒馆来"）

### 7.11 ⚠️ 用 PowerShell 改 JS 时的致命坑：`$(` 会被当子表达式吃掉

**现象**：用 `@" … "@`（双引号 here-string）往 `index.js` 里插 `$('#anko_pm_load').on('click',…)`，

更糟的是它会**连带吃掉下一行** ✓ → 绑定块被插到文件开头 ✗、还多出一个 `};` ✗。
`node --check` 仍然通过 ✓（语法恰好合法 ✗）→ 极难发现 ✗。

**规矩**：
1. 插含 `$(…)` / `$('…')` 的 **JS 代码，一律用单引号 here-string `@' … '@`** ✓（不插值 ✓），
2. 或者**按行号插入** ✓（`$lines[0..($i-1)] + $insert + $lines[$i..]` ✓，`$insert` 用单引号数组 ✓），
3. 改完**必须** `node --check` **并且**看一眼文件开头/插入点附近 ✓（这次就是开头被污染 ✓）。

### 7.12 ⚠️ 不要用 `presetManager.selectPreset(name)` 切预设（会崩）
